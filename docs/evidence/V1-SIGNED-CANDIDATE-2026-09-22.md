# Signed v1.0.0 candidate on the Windows laptop

This candidate remains unpublished. The release publish workflow was cancelled
before publication; the public release and source pin remain on
`v0.0.20-preview`. The tests below support readiness review only.

The [v1 draft build](https://github.com/omacom/try-omarchy-windows/actions/runs/35797778721) rebuilt the locked guest, passed its headless boot smoke, and uploaded draft assets. Their `SHA256SUMS` SHA-256 is `f388d0c041aa8b4a160fa743c6af1bcacf5c1b5d10a691c3f226b15727024e58`. Every downloaded draft asset matched its entry. The [Azure signing check](https://github.com/omacom/try-omarchy-windows/actions/runs/35798387169) passed at source commit `f23ef3d2dd13502a2b58c0770f87aa48287e2684`. The signed launcher SHA-256 is `d1753ae2121ad7e8d30558e5a9d0719db506d48bfc9293edced512fbe65168dc`; its Windows Authenticode status was Valid and both file version fields read `v1.0.0` on the laptop.

Testing used disposable copies of the AMD Ryzen 5 5625U Windows 11 laptop's existing installation. The original guest and recovery folders were not started or changed. A signed v0.0.19-preview launcher checked the public v0.0.20-preview feed on one copy, installed the bridge launcher, and booted the copy with GPU rendering. The resulting launcher SHA-256, `bef22fda3b22ce666dc195725be4e7f956945b1817c0af9f9912d2a15393c6dd`, matched the public bridge release. This exercised the current signed update feed before v1 publication.

Before the v1 install, the copied v20 guest wrote `~/Documents/v1-signed-preservation-marker.txt` with SHA-256 `88b499ed21948b6f19faeb230aecfa9b41dc23aaa9e8a564d6ec1a8cee84e705`. The signed v1 candidate downloaded the authenticated draft guest and runtime through a laptop loopback HTTP endpoint, using explicit SHA-256 pins and `-no-update`. It explicitly bypassed the laptop's older external QEMU so this test used its newly installed runtime. The bundled `qemu-system-x86_64w.exe` SHA-256 was `564d900a7839c100c716fd77aa0e40c3a24524eb540ea43347832562a966718c`, matching the r18 package. QEMU launched with WHPX, VirGL/Venus GPU display, and `virtio-pinch-pci`.

The v1 guest reached Hyprland and reported userspace readiness; only then did the launcher confirm the guest update. The marker retained its exact hash, and `systemctl --failed` showed no failed units. A native Windows screenshot showed the windowed desktop. Guest PipeWire and WirePlumber were active, playback and capture devices were present, and the Windows share mounted at `/mnt/host`. Vulkan playback of a two-second H.264 test through the normal systemd user session reached 100% and exited successfully. A raw SSH launch initially hung because it omitted the packaged `VN_PERF` and Vulkan loader environment inherited by desktop apps; that diagnostic run was terminated before repeating the test in the normal session.

Guest reboot returned to userspace with the marker intact. After activity settled, a 15-second QEMU sample consumed 2.375 CPU seconds, about 1.32% of the 12-thread host. Clean poweroff exited QEMU and the launcher. A second signed launch reused the installed payload, booted fullscreen, and reached userspace again with the marker unchanged. It fetched only `SHA256SUMS`, not the guest or runtime archives. A guest-side screenshot showed the full 1366×768 desktop; the Windows GDI screenshot of exclusive fullscreen was black, so the guest capture and QEMU's `-full-screen` argument establish the tested fullscreen result.

The user's physical two-finger pinch result for this exact r18 runtime package is recorded in [the r18 laptop acceptance](PINCH-R18-PHYSICAL-2026-09-22.md): easier gesture initiation than r17, zoom returned, and two-finger scrolling worked. Intel/NVIDIA Windows testing of r18 was unavailable at the user's request. This report does not claim coverage of that hardware or of the larger parity features listed in the release notes.

## Interrupted-update recovery and legacy bridge

A second disposable copy of the old installation completed Robocopy with 224 files inspected and zero failures. Its v20 guest booted under the public signed v20 launcher, had no failed systemd units, and wrote `~/Documents/v1-rollback-marker.txt` with SHA-256 `5e78f4635274e35af95138f4313920b9cc3d978bb7bb681bcec6e984067a6bd7`. The signed v1 candidate downloaded and installed both draft payloads on this copy. A separate watcher stopped its QEMU process three seconds after first boot began, before any userspace readiness signal, and stopped the candidate launcher. The durable state recorded `v1.0.0` with `guestPending`, `runtimePending`, and `started` all true; both `.previous` directories existed.

On the next signed-candidate launch, the log said `using restored guest and runtime for this recovery launch`. The previous guest and runtime booted with GPU display, reached userspace, and retained the marker hash. The active guest receipt again pointed to v0.0.20-preview with its original authenticated manifest digest, `bbdf1d478dc0a15fd105cde47057ab85190510b59742ffabf8da1a94117d2d49`; the restored runtime executable SHA-256 was `7b3aad5f42c1e7287ffb80dcbe73882deb8fe797cc55feff0ab8f5e1f53c0643`. The pending state and `.previous` directories were cleared. No guest service failed. This was a real interrupted first boot on a copied disk, not a hand-written rollback state.

The public signed v0.0.7-preview launcher (SHA-256 `83ddc93ce168f6721855d40ce69b04ea3cce79ee5eff44dc520856d7a0b62124`) then checked the public legacy `update.json` feed on this restored copy. It installed the exact signed v0.0.20-preview launcher, SHA-256 `bef22fda3b22ce666dc195725be4e7f956945b1817c0af9f9912d2a15393c6dd`, booted the copied guest with GPU display, and confirmed the launcher update after userspace readiness. A private QMP `system_powerdown` request shut down the guest cleanly. The original laptop installation remained untouched.
