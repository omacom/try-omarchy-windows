# File-drop correction, September 19, 2026

The physical Windows recording showed a received file trapped in a tiled transfer
window, an Application Not Responding dialog, and an empty Downloads folder.
This failed acceptance despite the earlier fallback-preservation tests passing.

The incoming path now launches a background receiver instead of a GTK window.
It resolves a local Files folder before downloading, verifies the transfer in
hidden staging on that filesystem, and atomically publishes each top-level item.
Existing names receive a numbered suffix. No clipboard paste or focus change is
involved. Unknown destinations use Downloads with a small notification.

Direct folder resolution currently requires one guest display and an unambiguous
local Nautilus location. Ambiguous tabs, duplicate folder titles, other apps and
nonlocal locations use Downloads. This does not emulate application-specific
imports or dropping onto a nested folder icon.

Windows progress waits two seconds before appearing, does not activate itself,
and closes immediately. Closing hides progress while copying continues; Cancel
stops the transfer. The explicitly opened outgoing-transfer window remains
available and hides immediately when closed during cancellation.

Validation:

- 153 guest tests passed, including native GTK, duplicate file/folder names,
  failure cleanup and background routing. Guest contract checks passed.
- Launcher tests and release-helper tests passed. Windows cross-vet passed using
  the repository's Win32 unsafe-pointer exception.
- Native Windows progress tests passed for cancellation and dismissing without
  cancelling the copy.
- A native WM_DROPFILES message to the running physical Windows QEMU window
  traversed the production bridge. The receiver reported the open Downloads
  folder, and the file appeared there without a guest transfer window.

The physical test uses guest scripts installed into the running test candidate.
Compatibility revision 28 delivers them through the next packaged guest update.
