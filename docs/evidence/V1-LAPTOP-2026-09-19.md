# V1 laptop acceptance, September 19, 2026

Follow-up to [preview 20 acceptance](PREVIEW20-CANDIDATE-2026-09-19.md).
Windows 11 Business 26200, AMD Ryzen 5 5625U, Radeon graphics, WHPX.
Tests use separate installations on the laptop's D: drive. Existing user
installations and the accepted preview-20 test guest are retained.

## Original pre-transfer launcher

The original signed v0.0.7-preview executable and its original factory image
were downloaded from the public release. Authenticode and the published launcher
checksum passed. The original bundled runtime reached the accelerated desktop.

| Item | Identity |
| --- | --- |
| Original launcher SHA256 | `83ddc93ce168f6721855d40ce69b04ea3cce79ee5eff44dc520856d7a0b62124` |
| Original kernel | `7.1.11-arch1-1` |
| Preserved guest file SHA256 | `ba514e27bfa43cc01ca2fab4f8f33cd14acfa06c05e20e03172a525545b27a23` |
| Published v20 launcher SHA256 | `bef22fda3b22ce666dc195725be4e7f956945b1817c0af9f9912d2a15393c6dd` |

V7 used its built-in `tsouth89` update URL and production signature-verification
key. No custom update feed or release override was supplied. It authenticated
the current metadata and replaced itself with the exact signed public v20
executable.

The first attempt was intentionally interrupted after launcher replacement and
runtime staging, before the new guest booted. Relaunch restored the original v7
executable and runtime, cleared both pending-update records and reached the old
desktop. The guest file retained its hash. This covers interruption before guest
readiness, not a power loss during guest OS package writes.

The uninterrupted retry passed. The upgraded guest reached its accelerated
desktop with kernel `7.2.6-arch2-1`; both compatibility/module markers read
`29:7.2.6-arch2-1`. The fixture retained its exact hash and systemd reported
`running`. Both launcher and payload updates were committed after userspace
readiness, and both pending-update records were removed.

**The first-update-across-repository-transfer gate is complete.** This does not
certify preview-to-stable or stable-to-stable updates, nor does updating the
launcher replace the existing guest OS with the latest factory distribution.

## Full-guest snapshot and storage checks

The native Windows test harness calls the production snapshot/restore and disk
preparation functions against the stopped public-v20 test installation. These are
backend acceptance checks, not a retest of every storage dialog.

- Created a complete snapshot containing the guest image, runtime, writable disk
  and saved settings. Archive size: `6587326027` bytes; SHA256:
  `a52c818d669824d3bec4e44ccba284d70034fed079175120603183d73360fe38`.
- During snapshot creation, Windows rejected a competing write handle to the
  source disk with sharing violation 32. The probe wrote no bytes.
- Restored the complete snapshot into a new installation. Restoration over the
  original installation was correctly refused. The source installation remained
  intact. The native test passed in 806.90 seconds.
- Grew the restored virtual disk from 24 to 32 GiB. A later 24 GiB request left
  the 32 GiB disk intact.
- Booted the restored installation with the signed public v20 launcher and its
  authenticated cached payload, without another payload download. The GPU desktop
  became available and systemd reported `running`. All three original guest
  fixtures retained their hashes.
- The guest reported a `34359738368`-byte disk and a `33709572096`-byte ext4
  filesystem, confirming filesystem growth beyond the old capacity.
- Reboot passed with the same expanded filesystem and all three fixture hashes
  intact; systemd again reported `running`.

The backend harness bypasses the restore dialog's shortcut finalization. Its first
launch paused at the shortcut-choice screen; the test recorded no new Windows
shortcuts and resumed. This was a harness setup step, not a guest restore failure.

## Full Hyper-V on the physical laptop

The full `Microsoft-Hyper-V-All` role was temporarily enabled with the user's
approval, followed by a Windows reboot. All seven Hyper-V components reported
`Enabled`, including the hypervisor, services and management tools. Both `vmms`
and `vmcompute` were running. Windows Hypervisor Platform and Virtual Machine
Platform remained enabled. No additional Hyper-V VM was created or run.

The exact signed public v20 executable passed against the restored test guest:

- First-attempt WHPX boot with `-cpu host`, virgl and Venus enabled. The visible
  Hyprland desktop used the DRM backend and reported GL 3.2.
- All three existing fixture hashes matched; the expanded filesystem remained
  intact and systemd reported `running`.
- Camera capture produced 30 distinct frames. A native Windows file-drop message
  delivered another copy with the expected hash and no blocking transfer window.
- Guest reboot relaunched QEMU and returned to the accelerated desktop. All four
  fixture hashes matched. Camera capture again produced 30 distinct frames.
- A six-second PipeWire playback completed successfully. Speaker sound was not
  physically checked during this test.
- Guest poweroff exited the launcher and QEMU cleanly.

After testing, the full Hyper-V role was disabled and Windows rebooted again.
All nine recorded Windows feature states matched the original baseline, with
Windows Hypervisor Platform and Virtual Machine Platform still enabled. SSHD was
returned to its original Manual startup setting. A final normal WHPX/GPU boot
passed with systemd `running`, the expanded filesystem and all four fixture hashes
intact.

This establishes full Hyper-V role coexistence on this AMD/Radeon laptop. It does
not establish Intel/Core Ultra or NVIDIA compatibility, simultaneous workloads
in another Hyper-V VM, or physical sleep/wake recovery.
