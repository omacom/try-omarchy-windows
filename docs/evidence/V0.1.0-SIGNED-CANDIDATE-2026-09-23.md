# Signed v0.1.0 candidate, September 22–23, 2026

This records acceptance of the private `v0.1.0` draft before its September 23
publication, followed by checks of the public release.

The [draft guest build](https://github.com/omacom/try-omarchy-windows/actions/runs/35814157354)
passed the locked guest build, asset checks, and headless instant-account boot.
The draft `SHA256SUMS` SHA-256 is
`3963f1d21fb280134201ebd65e5f339d3e88588e861f3e7681469a704ad7f6a9`.
Every downloaded draft asset matched its checksum. The
[final Azure signing check](https://github.com/omacom/try-omarchy-windows/actions/runs/35818607621)
used source commit `9ae72c386f3d7aebc353b2924112c35e77a4475c`. Its signed
launcher SHA-256 is
`1ec326b3f7cf0f517adeb8c1a96f97b33156ae5e81f5a13da7baa4424759dcdf`.
Windows reported a Valid Authenticode signature and `v0.1.0` for both file and
product versions. The signed test update manifest names that same launcher and
draft manifest hash.

Tests used an AMD Ryzen 5 5625U Windows 11 Business laptop, build 26200, with
Radeon driver `31.0.21921.1000`. Each operation used a disposable copy or new
test installation on its external D: drive. The existing installation, Start
Menu links, Desktop link, and retained recovery folders were not replaced.
The private draft assets were served over a Windows loopback tunnel with the
manifest SHA-256 explicitly supplied to the launcher. A dropped test tunnel
caused the first clean-install attempt to show a connection error before any
payload was installed; restarting after restoring the tunnel succeeded.

## Upgrade and clean install

A disposable copy of the public `v0.0.20-preview` guest was upgraded with the
first signed `v0.1.0` candidate. WHPX, VirGL/Venus, guest userspace readiness,
and preservation of `~/Documents/v1-rollback-marker.txt` passed. The marker
kept SHA-256
`5e78f4635274e35af95138f4313920b9cc3d978bb7bb681bcec6e984067a6bd7`.
The guest had no failed systemd units, PipeWire and WirePlumber were active,
playback and capture devices and the Windows camera were present, and the host
share was mounted. Writing a file through that share produced the same SHA-256
on Windows and inside the guest. The visible desktop and signed Settings window
were inspected; fullscreen and Windows sign-in launch controls were visible.
The upgrade committed only after guest userspace reported ready and shut down
cleanly afterward.

The first signed candidate had SHA-256
`6c48cea836de2b98c6b5ebe20025ecc557b4bb7410e41c9a1cd645088bb2eb4a`.
Its clean install downloaded and authenticated the draft payload, created the
writable guest disk, and booted a visible GPU desktop. Guest systemd was
`running` with no failed units; audio playback/capture, camera, and the host
share were present. A clean guest marker has SHA-256
`d7c3d98dd030ccf076e9bc8d1529ef6814c314704c610486d7256e93744e7ade`.
An explicit CPU-rendered second boot used `virtio-gpu-pci`, SDL `gl=off`, and
`tryomarchy.render=cpu`; it reached healthy userspace with the marker intact.

Selecting a Start Menu link in that clean install correctly refused to replace
links owned by the laptop's original installation, but offered the same choice
again on the next boot. [PR #162](https://github.com/omacom/try-omarchy-windows/pull/162)
fixed that issue. The final signed candidate created `Start Omarchy.lnk` and
`Settings.lnk` beside the clean test installation, both targeting its signed
stable launcher. The original Start Menu and Desktop link hashes were unchanged.
The shortcut choice marker was recorded. A second launch went straight to a
healthy GPU desktop without the prompt, and the clean guest marker retained its
hash. A brief QEMU window title during first boot was replaced by the branded
`Try Omarchy` title after startup settled.

## Interrupted update recovery

The final signed candidate installed both draft guest and runtime payloads on
another disposable `v0.0.20-preview` copy. A watcher stopped QEMU roughly
three seconds into its first new boot, before any userspace readiness signal,
and stopped the launcher. Durable state had `guestPending`, `runtimePending`,
and `started` true, with both `.previous` directories present. The next launch
logged `using restored guest and runtime for this recovery launch`, booted the
old GPU guest, reached healthy userspace, and retained the marker SHA-256 above.
The restored guest receipt again pointed to the public preview's authenticated
manifest, `bbdf1d478dc0a15fd105cde47057ab85190510b59742ffabf8da1a94117d2d49`.
The pending state and `.previous` directories were cleared, and the guest
powered off cleanly.

## Backup, restore, and uninstall

The final signed binary backed up the stopped clean installation to a
6,590,109,543-byte archive. It restored that archive to a separate folder,
placed signed `Start Omarchy.lnk` and `Settings.lnk` launchers beside that copy,
and showed the restored path in its success dialog. Its stable launcher had the
same SHA-256 as the final signed candidate. The restored guest booted with
`systemctl is-system-running` reporting `running`, zero failed units, active
PipeWire and WirePlumber, and the host share mounted at `/mnt/host`. The clean
guest marker retained SHA-256
`d7c3d98dd030ccf076e9bc8d1529ef6814c314704c610486d7256e93744e7ade`.
The restored guest SSH host-key fingerprint matched the clean installation.
It then powered off cleanly.

The final signed binary's uninstall dialog named only the restored folder.
After skipping another backup and confirming that exact path, it reported
success and removed that folder. The 6,590,109,543-byte archive and the clean
test installation remained. The original installation's global shortcuts
retained their pretest hashes.

## Publication and public checks

The final signed candidate passed the available physical Windows acceptance
checks. The [publish workflow](https://github.com/omacom/try-omarchy-windows/actions/runs/35846137627)
rebuilt and signed from the same source commit, then passed its public tagged
asset, legacy redirect, update-feed, and Latest download checks. The public
launcher SHA-256 is
`1341a87d90298267341714f5d1724b47969e934fa71cb52c0430fc65d4e61c9e`;
it differs from the candidate because the publish build had different VCS
metadata and a new signing timestamp. Windows reported Valid Authenticode and
`v0.1.0` for both file and product versions.
Both executables name the pinned source revision in Go build metadata. The
candidate reports `vcs.modified=false`; the published build reports
`vcs.modified=true`. The release workflow creates untracked `release-manifest/`
and `release/` staging directories before compiling, which accounts for the
dirty-worktree flag without a source change. This was reproduced by building
the pinned commit with and without generated files in `release-manifest/`.
A post-release ignore rule keeps these generated directories out of future
build provenance.

The public `update-v2.json` signature verified against the launcher's embedded
Ed25519 public key; it names the matching launcher hash and draft asset manifest
hash. The public `update.json` still names the signed `v0.0.20-preview` bridge.
The [site](https://tryomarchy.com/) shows `v0.1.0` and redirects `/download`
to the Latest launcher.

A separate copy of the public `v0.0.20-preview` installation was made on the
AMD Windows laptop with zero copy failures. Its signed launcher SHA-256 was
`bef22fda3b22ce666dc195725be4e7f956945b1817c0af9f9912d2a15393c6dd`
and its guest receipt named the public preview. With the update check due, that
launcher authenticated the public current feed, installed the exact public
`v0.1.0` launcher hash above, and downloaded the public guest and runtime.
The copied guest booted through the GPU path, reported healthy userspace, and
committed both launcher and payload updates. Both active receipts named the
public `v0.1.0` release and the guest receipt held the expected manifest hash.
No pending update state or `.previous` payload directory remained after
commit. The pre-existing `/home/omarchy/preserve-v7.txt` retained SHA-256
`ba514e27bfa43cc01ca2fab4f8f33cd14acfa06c05e20e03172a525545b27a23`,
matching the [September 19 record](V1-LAPTOP-2026-09-19.md). Systemd reported
`running` with zero failed units, PipeWire and WirePlumber were active, and
the Windows share was mounted. The guest powered off cleanly; a second launch
reached the same healthy GPU desktop without downloading again or prompting,
kept the file hash, and powered off cleanly. The published signed launcher then
uninstalled only this disposable copy after the exact target path was confirmed;
its success dialog appeared, while the original preview installation, global
shortcuts, existing backup, and saved test logs remained. Broader Windows 10
and Intel/NVIDIA testing were explicitly deprioritized by the user and are not
claimed here.
