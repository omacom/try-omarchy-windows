# Live audio r20 engineering check: September 23, 2026

This is an isolated candidate check on the AMD Ryzen 5 5625U Windows 11
laptop. Public `v0.2.0` remains on r19. The normal installation and public
runtime were not replaced. The engineering guest is the existing moved
`v0.0.20-preview` test guest, explicitly pinned to its recorded release and
manifest so it did not download a newer image during the audio test.

## Probe correction

The first checks ran `probe-audio-sessions.exe` through OpenSSH in Windows
session 0. QEMU was in the signed-in desktop's session 1, so those probes could
not enumerate its audio sessions. A supposedly missing session was a **test
error**, not proof of an r20 playback failure. The same incorrect probe also
missed sessions from the known-good r16 runtime. Repeating r16 with an
interactive, session-1 scheduled probe showed active Realtek playback and AMD
microphone sessions. All audio-session claims below use that interactive probe.

The first r20 build did have a separate real defect: an intentionally missing
output caused 149 fallback warnings, reopening the default on nearly every
poll. The corrected r20b source keeps the working fallback open until SDL
enumerates the selected endpoint again. It also retains the initial playback
device until the first stream; the effect on idle host-device use is noted
below.

## r20b physical results

- The candidate started with explicit `Speaker (Realtek(R) Audio)` output and
  `Microphone Array (AMD Audio Device)` input on the isolated guest. PipeWire
  enumerated a virtio stereo sink and source.
- Before guest capture, the interactive probe showed the Realtek playback
  session and no AMD microphone session. During generated guest playback it
  showed **active Realtek playback** in five consecutive samples. A second
  playback after idle also showed five active samples.
- A bounded guest capture delivered **1,130,496 bytes** of mono 48 kHz signed
  16-bit samples; the interactive probe showed **active AMD microphone** in
  repeated samples. The samples were discarded. After capture, the microphone
  session became inactive while playback could remain active.
- Changing the output route to a nonexistent SDL name during playback caused
  **one** fallback warning. The Windows default Realtek playback session stayed
  active during the stream; subsequent polls did not repeat the warning.
  Restoring the default route allowed another active playback run.
- Changing the input route to a nonexistent SDL name during capture caused
  **one** recording fallback warning. The Windows default AMD microphone
  session remained active, and the guest received **1,417,216 bytes** before
  the bounded capture ended. Subsequent polls did not repeat the warning.
- On a separate boot with **Allow microphone access** disabled, QEMU used
  `in.voices=0`. A bounded guest recording attempt returned **zero bytes** and
  the interactive probe showed no recording session. Playback remained
  available. QEMU's `Could not create a backend for voice 'virtio-sound.in'`
  messages are expected for this explicit input-disabled mode.
- Each guest boot ended with `systemctl poweroff`. The original audio and
  desktop preferences were restored byte-for-byte from test backups; both
  route files were set to `default`. No candidate launcher or QEMU process
  remained. Only the canceled, incomplete `guest.next` staging directory from
  an earlier accidental latest-image download was removed.

## Remaining boundaries

There is only one active physical speaker and microphone on this laptop, so
switching between two real outputs or inputs, and physical unplug/reconnect,
remain untested. The interactive audio session proves the route is open, not
that a person heard smooth playback or intelligible microphone audio. The
corrected patch keeps the initial playback device open until the first stream;
idle device release before any playback is not established. This PR only makes
host Settings route changes live. It does not yet show Windows endpoints in
the guest PipeWire picker or handle host default changes through an endpoint
notification bridge. r20b is an engineering artifact, not a published or
pinned runtime.
