# Shared files in Windows apps

[Issue #375](https://github.com/omacom/try-omarchy-windows/issues/375) lets Omarchy ask Windows to open a file in the shared folder. The guest side ships separately; the Windows settings alone do not add a file-opening action inside Omarchy.

In Windows **Try Omarchy Settings → Apps**, the **Files in Windows** section lists allowed file types and their openers. Choose a file type and **Default Windows app**, or choose an app from **Approved Windows apps**, then choose **Add file type** and save Settings. The default uses the current Windows file association. To stop allowing a type, select its row, choose **Remove selected** and save. Removing an approved app also removes the file types assigned to it; they never switch to the default app. Opening a file reveals Windows; use the tray icon to return to Omarchy.

Only types from a fixed, reviewed catalog can be allowed: PDF, plain text and Markdown, CSV, modern Office documents without macro-enabled extensions, common raster images, audio and video. Executables, scripts, installers, shortcuts, system files, disk images, archives (including ZIP), RTF, legacy or macro-enabled Office documents, other active document formats, web pages and SVG are never allowed. Approving an app does not expand the catalog. Interpreters cannot be file openers, and an opener cannot overlap the folder shared with the running guest.

Approvals stay in `approved-file-types.json` beside that installation's settings. Each entry pairs an extension with either the Windows default or an approved app ID. They move with the installation, are removed when it is uninstalled, and are excluded from backups. Portable installations use the same file-opening settings as installed copies. Saving changes applies to a running guest on the next approved-app sync, at most about 30 seconds later. The host reloads both approval lists for every request, so revocation blocks new opens as soon as it is saved. An app ID that is no longer approved is refused, never treated as the default.

The guest receives only the allowed extensions. A request contains one bounded, encoded relative path, without an executable path or command-line options. The host checks the request, limits how often files can be opened, and uses the shared folder from the running boot. It rejects absolute paths, traversal, alternate data streams, reserved names and malformed components. It walks the share and requested path with metadata handles, rejects symbolic links, junctions and unsupported reparse points, and permits OneDrive placeholder tags that do not redirect paths. The final target must be an ordinary file with one hard link on a local drive. The final share path must match the configured share, and the final file path must match the request, using Windows ordinal case-insensitive comparison. Short-name aliases and substituted drive paths are refused. Explicit openers must still be approved local executables; the host passes the file path as one argument without a shell.

Allowing a type lets Omarchy ask to open any file of that type in the shared folder, not just a file selected in a particular guest app. The Windows app runs outside the guest and handles the file contents. The user chooses which reviewed types to approve, and the receiving app decides what the file does; an allowed extension is not a check of the contents. In particular, allowing `.csv` is a choice to accept spreadsheet-formula risks when a spreadsheet app opens the file. Guest-created files may lack Mark-of-the-Web, so Windows and apps may not show the warnings used for downloaded files.

The host closes its validation handles before the Windows app reopens the file by path. A file swapped in that gap can be opened. These checks constrain the request and its path; they do not remove that race or make the receiving Windows app a sandbox.
